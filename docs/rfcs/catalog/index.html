    NG911 RFCs by category

    Representation (11)

    • RFC 4119: A Presence-based GEOPRIV Location Object Format (PIDF-LO) (November 2005)
      Defines PIDF-LO (Presence Information Data Format–Location Object) extending PIDF (Presence Information Data Format) with geopriv location, usage-rules, baseline GML (Geography Markup Language) support, and S/MIME (Secure/Multipurpose Internet Mail Extensions) security
    • RFC 4589: Location Types Registry (July 2006)
      Creates an IANA (Internet Assigned Numbers Authority) registry and XML (Extensible Markup Language) schema for standardized location type tokens
    • RFC 5139: Revised Civic Location Format for PIDF-LO (February 2008)
      Revises the PIDF-LO (Presence Information Data Format-Location Object) civic address schema with new elements, thoroughfare hierarchy, language tagging, and country/subdivision constraints
    • RFC 5491: PIDF-LO Usage Clarification, Considerations, and Recommendations (March 2009)
      Constrains PIDF-LO (Presence Information Data Format-Location Object) usage and GML (Geography Markup Language) shapes for interoperable, routing-ready Internet location
    • RFC 5774: Civic Address Considerations for PIDF-LO and IANA Registry Definition (BCP 154) (March 2010)
      Guidelines and an IANA (Internet Assigned Numbers Authority) registry for national civic-address mappings in PIDF-LO (Presence Information Data Format-Location Object), including a complete Austrian mapping
    • RFC 5808: Requirements for a Location-by-Reference Mechanism (May 2010)
      Requirements for LbyR (Location-by-Reference) using a location URI (Uniform Resource Identifier) to retrieve location via configuration and dereference with privacy and security controls
    • RFC 5870: A Uniform Resource Identifier for Geographic Locations ('geo' URI) (June 2010)
      Defines the 'geo' URI (Uniform Resource Identifier) for coordinates in a default CRS (Coordinate Reference System) of WGS-84 (World Geodetic System 1984), with optional uncertainty and parameter registry
    • RFC 5962: Dynamic Extensions to PIDF-LO (September 2010)
      Adds dynamic motion elements to PIDF-LO (Presence Information Data Format-Location Object) for orientation, speed, and heading
    • RFC 6848: Specifying Civic Address Extensions in PIDF-LO (January 2013)
      Defines extensible civic-address elements for PIDF-LO (Presence Information Data Format–Location Object), adds DHCP (Dynamic Host Configuration Protocol) CAtype 40 for lossless translation, and requires namespace-qualified validation in LoST (Location-to-Service Translation)
    • RFC 7035: Relative Location Representation (October 2013)
      Extends PIDF-LO (Presence Information Data Format‑Location Object) to encode relative offsets from a reference, with XML (eXtensible Markup Language) and TLV (Type‑Length‑Value) formats plus optional map alignment metadata
    • RFC 7459: Representation of Uncertainty and Confidence in PIDF-LO (February 2015)
      Defines uncertainty and confidence for PIDF-LO (Presence Information Data Format-Location Object), adds a confidence element with PDF (Probability Density Function) type, and algorithms for manipulating uncertain location

    Acquisition (13)

    • RFC 4676: DHCP Option for Civic Addresses Configuration Information (October 2006)
      Defines DHCP (Dynamic Host Configuration Protocol) options to convey structured civic address location with language/script variants to clients
    • RFC 4776: DHCPv4 and DHCPv6 Option for Civic Addresses Configuration Information (November 2006)
      Defines DHCPv4 (Dynamic Host Configuration Protocol v4) and DHCPv6 options to deliver civic/postal location (LCI: Location Configuration Information) with multi-language/script support for emergency and presence uses (§1, §3)
    • RFC 5223: Discovering LoST Servers Using DHCP (August 2008)
      Defines LoST (Location-to-Service Translation) server discovery via DHCP (Dynamic Host Configuration Protocol) by delivering a DNS (Domain Name System) domain name for subsequent resolution
    • RFC 5985: HTTP-Enabled Location Delivery (HELD) (September 2010)
      Defines HELD (HTTP-Enabled Location Delivery), an L7 LCP (Layer 7 Location Configuration Protocol) to fetch device location from a LIS (Location Information Server) by value (PIDF-LO: Presence Information Data Format-Location Object) or by reference (URI: Uniform Resource Identifier)
    • RFC 5986: Discovering the Local Location Information Server (LIS) (September 2010)
      Defines LIS (Location Information Server) discovery using DHCP (Dynamic Host Configuration Protocol) and U-NAPTR (URI-enabled Naming Authority Pointer) to obtain a HELD (HTTP-Enabled Location Delivery) URI
    • RFC 6155: Use of Device Identity in HELD (March 2011)
      Extends HELD (HTTP-Enabled Location Delivery) so a LIS (Location Information Server) can locate a target using explicit Device identifiers with privacy and authorization controls
    • RFC 6225: DHCP Options for Coordinate-Based Location Configuration Information (July 2011)
      Defines DHCP (Dynamic Host Configuration Protocol) v4/v6 options for coordinate-based LCI (Location Configuration Information) with uncertainty, resolution, altitude types, and datum handling (§2.1–§2.5)
    • RFC 6753: A Location Dereference Protocol Using HELD (October 2012)
      Defines dereferencing a location URI (Uniform Resource Identifier) via HELD (HTTP-Enabled Location Delivery) over HTTP (Hypertext Transfer Protocol)/TLS (Transport Layer Security) to obtain a PIDF-LO (Presence Information Data Format-Location Object)
    • RFC 6915: Flow Identity Extension for HELD (April 2013)
      Extends HELD (HTTP-Enabled Location Delivery) with a flow identity to identify a Device by the full 6‑tuple across NAT (Network Address Translation)
    • RFC 7105: Using Device-Provided Location-Related Measurements in LCPs (January 2014)
      Standardizes an XML container and schemas for device-provided measurements in LCP (Location Configuration Protocol) requests to a LIS (Location Information Server), with provenance, requests, and privacy/security controls
    • RFC 7199: Location Configuration Extensions for Policy Management (April 2014)
      Defines policy URIs and HELD (HTTP-Enabled Location Delivery) extensions so LCP (Location Configuration Protocol) clients manage location-by-reference authorization via HTTP (Hypertext Transfer Protocol) GET/PUT/DELETE
    • RFC 7216: LIS Discovery Using IP Addresses and Reverse DNS (April 2014)
      Defines reverse DNS (Domain Name System)–based domain inputs from device IP addresses to discover an access-network LIS (Location Information Server) via DDDS (Dynamic Delegation Discovery Service), including prefix-shortening in in-addr.arpa/ip6.arpa (§4–§4.3)
    • RFC 7840: A Routing Request Extension for HELD (May 2016)
      Extends HELD (HTTP-Enabled Location Delivery) to let a LIS (Location Information Server) return PSAP (Public Safety Answering Point) routing URIs with location, reducing dependency on LoST (Location-to-Service Translation) (§1, §4)

    Routing (12)

    • RFC 5031: A Uniform Resource Name (URN) for Emergency and Other Well-Known Services (January 2008)
      Defines a service URN (Uniform Resource Name) namespace to label emergency and other well-known services (e.g., urn:service:sos) for protocol-agnostic identification and resolution (§1, §3)
    • RFC 5222: LoST: A Location-to-Service Translation Protocol (August 2008)
      Defines LoST (Location-to-Service Translation) XML/HTTP protocol that maps service URNs and civic/geodetic location to service URIs, including service boundaries, caching, validation, and redirects, to identify the correct PSAP (Public Safety Answering Point) (§1, §3, §5–§9, §13.3, §14)
    • RFC 5223: Discovering LoST Servers Using DHCP (August 2008)
      Defines LoST (Location-to-Service Translation) server discovery via DHCP (Dynamic Host Configuration Protocol) by delivering a DNS (Domain Name System) domain name for subsequent resolution
    • RFC 5964: Specifying Holes in LoST Service Boundaries (August 2010)
      Profiles LoST (Location-to-Service Translation) service boundaries with holes in GML (Geography Markup Language) and a selection algorithm
    • RFC 6197: LoST Service List Boundary Extension (April 2011)
      Extends LoST (Location-to-Service Translation) with a Service List Boundary so clients learn the geographic scope and lifetime of listServicesByLocation results
    • RFC 6281: LoST: An Extension for Finding Geographically Relevant Speakers of a Language (June 2011)
      Describes BTMM (Back to My Mac) using IPv6 ULA (Unique Local Address) identifiers, IPsec (Internet Protocol Security), and UDP (User Datagram Protocol) encapsulation to enable secure mobility across Network Address Translators
    • RFC 6442: Location Conveyance for the Session Initiation Protocol (SIP) (December 2011)
      Adds SIP (Session Initiation Protocol) extensions to carry caller location by value or reference and to control location-based routing via Geolocation, Geolocation-Routing, and Geolocation-Error, plus a 424 error for bad location (§1, §4.1–§4.4)
    • RFC 6739: Synchronizing Service Boundaries and Elements Based on LoST (October 2012)
      Defines the LoST (Location-to-Service Translation) sync protocol to exchange authoritative mapping elements and service boundary data for correct PSAP (Public Safety Answering Point) selection
    • RFC 7163: URN for Country-Specific Emergency Services (March 2014)
      Updates RFC (Request for Comments) 5031 to allow sos service URN (Uniform Resource Name) registrations for country-specific emergency services (§3.2)
    • RFC 7840: A Routing Request Extension for HELD (May 2016)
      Extends HELD (HTTP-Enabled Location Delivery) to let a LIS (Location Information Server) return PSAP (Public Safety Answering Point) routing URIs with location, reducing dependency on LoST (Location-to-Service Translation) (§1, §4)
    • RFC 8917: The LoST-Validation S-NAPTR Application Service Tag (October 2020)
      Registers the LoST-Validation S-NAPTR (Straightforward-Naming Authority PoinTeR) tag so LoST (Location-to-Service Translation) clients can discover DNS (Domain Name System) NAPTR (Naming Authority Pointer) records for servers designated for location validation
    • RFC 9036: Changing the LoST Location Profiles Registry Policy (June 2021)
      Changes policy of the Location-to-Service Translation (LoST) Location Profiles registry to Specification Required to allow other standards bodies to register profiles

    Conveyance (13)

    • RFC 5580: Carrying Location Objects in RADIUS and Diameter (August 2009)
      Defines attributes to carry location and privacy policy in RADIUS (Remote Authentication Dial-In User Service) and Diameter (AAA: Authentication, Authorization, and Accounting protocol) authentication and accounting messages
    • RFC 5606: Implications of 'retransmission-allowed' for SIP Location Conveyance (August 2009)
      Clarifies how retransmission-allowed in PIDF-LO (Presence Information Data Format-Location Object) applies when location is conveyed via SIP (Session Initiation Protocol) and proposes signaling to permit location-based routing
    • RFC 5808: Requirements for a Location-by-Reference Mechanism (May 2010)
      Requirements for LbyR (Location-by-Reference) using a location URI (Uniform Resource Identifier) to retrieve location via configuration and dereference with privacy and security controls
    • RFC 6442: Location Conveyance for the Session Initiation Protocol (SIP) (December 2011)
      Adds SIP (Session Initiation Protocol) extensions to carry caller location by value or reference and to control location-based routing via Geolocation, Geolocation-Routing, and Geolocation-Error, plus a 424 error for bad location (§1, §4.1–§4.4)
    • RFC 6447: Filtering Location Notifications in SIP (January 2012)
      Defines XML filters for SIP (Session Initiation Protocol) presence to send PIDF-LO (Presence Information Data Format‑Location Object) updates only on meaningful movement, speed, region, element, or type changes, with notification rate control
    • RFC 6753: A Location Dereference Protocol Using HELD (October 2012)
      Defines dereferencing a location URI (Uniform Resource Identifier) via HELD (HTTP-Enabled Location Delivery) over HTTP (Hypertext Transfer Protocol)/TLS (Transport Layer Security) to obtain a PIDF-LO (Presence Information Data Format-Location Object)
    • RFC 7090: Public Safety Answering Point (PSAP) Callback (April 2014)
      Defines a SIP (Session Initiation Protocol) Priority header value psap-callback to mark PSAP (Public Safety Answering Point) callbacks for preferential treatment with safeguards (§4.1–§4.3)
    • RFC 7852: Additional Data Related to an Emergency Call (July 2016)
      Defines XML additional-data blocks and transport via SIP (Session Initiation Protocol) and PIDF-LO (Presence Information Data Format-Location Object) to PSAP (Public Safety Answering Point)
    • RFC 8147: Next-Generation Pan-European eCall (May 2017)
      Defines NG‑eCall (next‑generation in‑vehicle emergency calling) over SIP (Session Initiation Protocol), enabling vehicle data and control exchange via a control XML and an INFO (SIP INFO) package between IVS (In‑Vehicle System) and PSAP (Public Safety Answering Point)
    • RFC 8148: Next-Generation Vehicle-Initiated Emergency Calls (May 2017)
      Defines next-generation vehicle-initiated emergency calling via ACN (Automatic Crash Notification) with mandatory VEDS (Vehicle Emergency Data Set), transported using SIP (Session Initiation Protocol) Call-Info, INFO package, and metadata/control for PSAP requests and acknowledgments (§1, §7–§9, §14.7)
    • RFC 8559: RADIUS Attributes for Carrying Location Information (Updates RFC 5580) (April 2019)
      Enables realm-based proxying of RADIUS (Remote Authentication Dial-In User Service) Change-of-Authorization and Disconnect messages using Operator-Name and a new Operator-NAS-Identifier
    • RFC 8787: Location Source Parameter for the SIP Geolocation Header Field (May 2020)
      Adds the loc-src parameter so SIP (Session Initiation Protocol) intermediaries can identify, by hostname, which node inserted each locationValue in the Geolocation header within trusted emergency-calling domains
    • RFC 8876: Non-Interactive Emergency Calls (September 2020)
      Defines a SIP (Session Initiation Protocol) MESSAGE carrying CAP (Common Alerting Protocol) data for non-interactive emergency calls, including transport via Call-Info, CAP profiling, and new error signaling (§4–§5)

    Framework (12)

    • RFC 5012: Requirements for Emergency Context Resolution with Internet Technologies (January 2008)
      Sets requirements for ECRIT (Emergency Context Resolution with Internet Technologies): location-based mapping to PSAP (Public Safety Answering Point) URIs and use of service identifiers for IP emergency calls (§1)
    • RFC 5069: Security Threats and Requirements for Emergency Call Marking and Mapping (January 2008)
      Identifies threats and defines security requirements for emergency call marking and location-to-PSAP (Public Safety Answering Point) URI (Uniform Resource Identifier) mapping on the Internet
    • RFC 5582: Location-to-URL Mapping Architecture and Framework (September 2009)
      Architects a global LoST (Location-to-Service Translation) hierarchy—seekers, resolvers, trees, and forest guides—for mapping location and service identifiers to service URIs (Uniform Resource Identifiers) (§1, §4.1)
    • RFC 5687: GEOPRIV L7 Location Configuration Protocol: Problem Statement and Requirements (March 2010)
      Problem statement and requirements for a Layer 7 Location Configuration Protocol (L7 LCP: device–Location Information Server exchange) enabling devices to obtain location from a LIS (Location Information Server) for LoST (Location-to-Service Translation) and SIP (Session Initiation Protocol) (§1)
    • RFC 6280: An Architecture for Location and Location Privacy in Internet Applications (BCP 160) (July 2011)
      Defines a privacy-focused Internet location architecture (“Geopriv”) with roles, a location life cycle, rule-bound location objects, and security requirements for positioning, distribution, and use
    • RFC 6443: Framework for Emergency Calling Using Internet Multimedia (December 2011)
      Defines an Internet emergency-calling framework: how SIP (Session Initiation Protocol), LIS (Location Information Server), and LoST (Location-to-Service Translation) enable location acquisition, routing, conveyance, security, media, and callbacks (§3, §6–§10, §14)
    • RFC 6881: Best Current Practice for Communications Services in Support of Emergency Calling (BCP 181) (March 2013)
      Best current practice for Internet emergency calling using SIP (Session Initiation Protocol), defining end-to-end location, mapping via LoST (Location-to-Service Translation), HELD (HTTP-Enabled Location Delivery), and routing to PSAPs (Public Safety Answering Points)
    • RFC 7090: Public Safety Answering Point (PSAP) Callback (April 2014)
      Defines a SIP (Session Initiation Protocol) Priority header value psap-callback to mark PSAP (Public Safety Answering Point) callbacks for preferential treatment with safeguards (§4.1–§4.3)
    • RFC 7378: Trustworthy Location (December 2014)
      Analyzes threats and mitigations for trustworthy location in IP emergency calling, highlighting LbyR (location-by-reference) via HELD (HTTP-Enabled Location Delivery) and guidance for assessing location trust
    • RFC 7406: Extensions for Unauthenticated and Unauthorized Devices (December 2014)
      Extends the Internet emergency calling architecture to handle unauthenticated or unauthorized callers, defining device, access, and routing behavior for location, mapping, and call setup
    • RFC 8147: Next-Generation Pan-European eCall (May 2017)
      Defines NG‑eCall (next‑generation in‑vehicle emergency calling) over SIP (Session Initiation Protocol), enabling vehicle data and control exchange via a control XML and an INFO (SIP INFO) package between IVS (In‑Vehicle System) and PSAP (Public Safety Answering Point)
    • RFC 9036: Changing the LoST Location Profiles Registry Policy (June 2021)
      Changes policy of the Location-to-Service Translation (LoST) Location Profiles registry to Specification Required to allow other standards bodies to register profiles
