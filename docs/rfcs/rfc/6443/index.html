    RFC 6443: Framework for Emergency Calling Using Internet Multimedia

    Informational December 2011

    Framework

    Abstract: The IETF has standardized various aspects of placing emergency calls. This document describes how all of those component parts are used to support emergency calls from citizens and visitors to authorities. This document is not an Internet Standards Track specification; it is published for informational purposes.

    Summary tagline

    Defines an Internet emergency-calling framework: how SIP (Session Initiation Protocol), LIS (Location Information Server), and LoST (Location-to-Service Translation) enable location acquisition, routing, conveyance, security, media, and callbacks (§3, §6–§10, §14)

    Problems

    Internet multimedia emergency calling lacks a unified method to recognize emergencies, route to the correct PSAP (Public Safety Answering Point), convey accurate caller location, and support reliable call-backs across heterogeneous providers and devices (§1). Mobility, varied local dial strings (mapped via URN: urn:service:sos), and location acquisition via LCPs (Location Configuration Protocols) are complicated by roaming, NAT (Network Address Translator), and VPN (Virtual Private Network) tunneling, making dial-string recognition, location determination, and routing via LoST error-prone (§3, §5–§8).

    Contributions

    Defines an end-to-end architecture and message flow using SIP (Session Initiation Protocol) with a service URN (urn:service:sos), the SIP Geolocation header, and LoST (Location-to-Service Translation) mapping to route calls to the appropriate authority (§3, §8–§9.2). Specifies location acquisition via LCPs such as DHCP civic/geo, HELD (HTTP-Enabled Location Delivery), and LLDP-MED; discovery of LIS (Location Information Server) and LoST via DHCP; and location validation and defaulting (§6.5–§6.12, §7). Describes location conveyance by-value/by-reference, mid-call updates (including ResponseTime = emergencyDispatch for HELD dereference), handling multiple/conflicting locations, and PSAP callback identifiers via Contact, From, and GRUU (Globally Routable UA URI) (§6.4, §6.8–§6.9, §10). Recommends hop-by-hop TLS (Transport Layer Security) for signaling with fallback if needed, and outlines media expectations (RTP, real-time text, IM, video) and SRTP/DTLS for media security (§9.1, §14).
